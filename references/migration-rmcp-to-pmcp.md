# Migrating outdated rmcp-style material to PAIML PMCP

Use this when modernizing older skills, examples, or Rust MCP servers.

## Fast diagnosis

Outdated patterns commonly include:

- `rmcp = ...` or `rmcp-macros = ...` dependencies.
- `use rmcp::{tool, tool_router, tool_handler}`.
- `#[tool]`, `#[tool_router]`, `#[tool_handler]`.
- `ServerHandler`, `ToolRouter`, `RoleServer`, `RequestContext`.
- `Parameters<T>` wrapper in tool signatures.
- `StdioTransport::new()` plus `Server::builder().with_handler(...).build(transport)`.
- `.gitignore` excluding `Cargo.lock` for a binary server.

For PAIML PMCP, replace those with `pmcp`, `#[mcp_tool]`, `#[mcp_server]`, `TypedTool`, `ServerBuilder`, and `server.run_stdio()`/Streamable HTTP APIs as appropriate.

## Macro mapping

| Old rmcp-ish concept | PMCP direction |
|---|---|
| `#[tool]` | `#[mcp_tool]` |
| `#[tool_router]` | `#[mcp_server]` on an `impl` block |
| `#[tool_handler]` | Generated by `#[mcp_server]` or replaced by builder registration |
| `Parameters<T>` | Plain typed args struct, e.g. `async fn foo(&self, args: FooArgs)` |
| `Result<T, String>` | `pmcp::Result<T>` with typed output |
| `ServerHandler` impl for everything | Register tools/prompts/resources via PMCP builder or traits |
| SSE-first examples | stdio for local, Streamable HTTP for production remote |

## Migration workflow

1. Check the user's constraint. If they explicitly need official `rmcp`, stop and use that SDK. Otherwise use PAIML PMCP.
2. Read `Cargo.toml`, `Cargo.lock`, and current imports.
3. Replace dependencies with `pmcp = { version = "=2.17.0", features = [...] }`, then choose the smallest exact feature set needed by the server and verify Rust 1.91 compatibility.
4. Convert input wrappers to plain `Deserialize + JsonSchema` structs.
5. Convert genuinely structured output to typed `Serialize + JsonSchema` structs that emit both `structuredContent` and canonical JSON text. Keep text-only output text-only; do not invent a `serde_json::Value` schema.
6. Convert errors to `pmcp::Result<T>`.
7. Register with `#[mcp_server]` or `ServerBuilder`.
8. Replace ad-hoc transport setup with current stdio or Streamable HTTP setup. Keep local stdio stdout protocol-only and defer HTTP/OAuth unless a remote use case exists.
9. Rebuild tests against protocol behavior, not just handler functions.
10. Run fmt, clippy, tests, and scenario tests.

## Common fixes

### Cargo features

Do not use `full` by default in production. Use it only while prototyping or when all included functionality is justified.

### Descriptions

Modern PMCP macro versions can harvest rustdoc descriptions, but explicit descriptions remain better when the tool needs client-facing wording or side-effect warnings.

### Validation

Prefer schema-level validation for simple types and explicit Rust validation for cross-field constraints. Since 2.15, publish `outputSchema` only for truthful dual-emitted structured output. Cached-output validation is warn-only and never rejects or mutates the server result; test client-side rejection separately if the client validates. A `ToolOutput::Result` path bypasses response middleware, so use it intentionally and cover it with a protocol snapshot.

### Resources and prompts

Do not fake resources as tools. Use resources for URI-addressable content and prompts for reusable templates/workflows.

### Client compatibility

PMCP tracks TypeScript SDK wire compatibility. Keep protocol-visible schemas stable and use scenario/schema diff tests to avoid breaking clients.
